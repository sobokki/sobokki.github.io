회사 제품들의 DB를 보관하고, 필요한 시점의 데이터를 확인하는 내부 도구를 만들고 있다.

백업 파일에는 많은 데이터가 담길 수 있다. 로그인 화면을 만드는 것뿐 아니라, 누가 접근할 수 있고 어떤 제품의 데이터를 볼 수 있는지까지 생각해야 했다.

이번 글에서는 로그인 기능을 구현하며 정리한 쿠키·세션·JWT의 개념과 실제 인증 구조, 앞으로 보완할 보안 과제를 다룬다.

현재는 로컬 개발 단계이며 운영 보안 검증을 마친 제품을 소개하는 글은 아니다.

## 1. 쿠키·세션·JWT는 같은 종류의 선택지가 아니었다

처음에는 세 가지를 서로 다른 로그인 방식으로 생각했다. 하지만 각각 맡는 역할이 다르다.

| 개념 | 역할 |
|---|---|
| 쿠키 | 브라우저가 작은 데이터를 보관하고, 조건에 맞는 요청에 자동으로 보내는 수단 |
| 서버 세션 | 서버가 관리하는 로그인 상태 |
| JWT | 정보를 담는 토큰 형식. 서명된 JWT는 서명과 만료 시간 등을 검증해서 사용 |

서버 세션 방식에서는 보통 쿠키에 세션 ID를 담는다.

브라우저가 그 ID를 보내면 서버는 자신의 저장소에서 로그인 기록을 찾는다. 해당 기록이 존재하고 유효한지 확인하는 것이다. 저장소는 DB, Redis, 서버 메모리 등으로 구성할 수 있다.

JWT도 쿠키에 담을 수 있다.

따라서 “쿠키 방식인가요, JWT 방식인가요?”라는 질문에는 둘 중 하나를 고르는 대신 **JWT를 쿠키에 저장해서 사용하는 구조인지** 설명해야 한다.

참고: [MDN — 인증](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication)

## 2. 로그인 방법과 로그인 상태 유지 방법도 구분했다

우리 제품은 등록된 이메일과 비밀번호로 사용자를 확인한다.

회사 이메일처럼 생긴 주소를 입력했다고 바로 로그인되는 것은 아니다. 관리자가 사전에 등록한 계정이고, 계정이 유효하며, 비밀번호가 맞아야 한다.

다만 이 방식은 회사 메일함의 소유권을 직접 인증하는 것은 아니다. 계정 등록 단계에서 관리자가 사용자를 확인하는 구조다. 회사 계정 제공자와 연동하는 SSO와도 다르다.

로그인에 성공한 이후의 상태를 유지하는 데 JWT와 서버 세션을 사용했다.

```text
이메일·비밀번호 입력
        ↓
등록된 계정과 비밀번호 확인
        ↓
JWT 발급 및 서버 세션 생성
        ↓
브라우저의 HttpOnly 쿠키에 JWT 저장
        ↓
업무 요청에 쿠키 자동 전송
        ↓
JWT 검증 + 서버 세션 확인
        ↓
요청한 제품과 작업에 대한 권한 확인
```

비밀번호는 검증용 해시로 저장하며, JWT 안에 넣지 않는다.

## 3. JWT에 서명이 있다고 내용이 숨겨지는 것은 아니다

서명과 암호화도 혼동하기 쉬웠다.

- 서명은 내용이 변조되지 않았는지 검증하는 데 사용한다.
- 암호화는 내용을 알아볼 수 없게 숨기는 데 사용한다.

우리 제품에서 사용하는 JWT는 서명되어 있지만 암호화된 토큰은 아니다. 토큰을 가진 사람은 내용을 읽을 수 있다.

누군가 토큰의 만료 시각을 바꾸면 서명 검증에 실패한다. 하지만 내용을 읽는 것 자체가 막히는 것은 아니다.

그래서 비밀번호 같은 민감한 정보를 JWT에 넣으면 안 된다.

또한 서명이 정상이라는 사실만으로 지금 토큰을 보내는 사람이 원래 로그인한 본인인지까지 알 수는 없다. 누군가 유효한 토큰을 훔쳐 그대로 보내면, 서명만으로는 도난 여부를 구분할 수 없다.

## 4. JWT와 서버 세션을 함께 사용하는 이유

JWT는 발급된 토큰 목록을 조회하지 않고도 서명을 검증할 수 있다.

그렇다면 왜 서버에 세션을 추가로 저장했을까? 로그아웃 처리를 생각하면 이유가 명확해진다.

예를 들어 오후 3시에 로그인해서 3시 30분에 만료되는 JWT를 받았다고 하자. 사용자는 3시 10분에 로그아웃했다.

브라우저의 쿠키를 삭제하더라도, 누군가 미리 복사한 JWT까지 지울 수는 없다. 서버가 서명과 만료 시간만 확인한다면 그 토큰은 여전히 검증을 통과할 수 있다.

우리 제품은 JWT 안의 식별자로 연결된 서버 세션도 확인한다.

```text
JWT 서명이 정상인가?
        ↓
만료되지 않았는가?
        ↓
서버에 연결된 유효한 세션이 있는가?
        ↓
사용자 계정이 유효한가?
```

로그아웃하면 서버에서 해당 세션을 삭제한다. 따라서 JWT 자체의 서명과 만료 시간이 정상이더라도 이후 요청을 거부할 수 있다.

비밀번호를 변경하면 해당 사용자의 기존 세션을 모두 종료하도록 했다.

이 구조는 로그아웃한 토큰의 재사용을 막는 데 도움이 된다. 다만 세션이 여전히 유효한 상태에서 탈취한 토큰을 사용하는 것까지 자동으로 구분해 주지는 않는다.

참고: [OWASP — 세션 관리](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

## 5. 로그인 후 30분이면 다시 인증하도록 했다

현재 제품은 로그인 시점부터 30분이 지나면 만료되는 절대 만료 정책을 사용한다. 자동 갱신으로 로그인 시간을 연장하지 않는다.

오후 3시에 로그인했다면 3시 20분에 작업해도 만료 시각은 3시 30분이다.

이는 마지막 활동 이후 일정 시간 동안 활동이 없으면 종료하는 비활동 만료와 다르다.

이미 발급한 JWT의 만료 시각도 사용자가 활동한다고 저절로 바뀌지 않는다. 로그인 상태를 계속 연장하려면 서버 세션의 기한을 조정하거나 새 토큰을 발급하는 별도 구현이 필요하다.

DB 백업을 다루는 제품이라는 점을 고려해, 사용 편의성보다 재인증 간격을 제한하는 쪽을 선택했다. 대신 작업 중 다시 로그인해야 하는 불편이 생긴다.

30분은 모든 서비스에 적용되는 보안 정답이 아니라, 현재 제품에서 선택한 값이다. 비활동 만료와 추가 인증을 함께 적용할 필요도 계속 검토해야 한다.

## 6. HttpOnly는 토큰을 숨기는 암호화가 아니다

JWT는 HttpOnly 쿠키에 저장했다.

HttpOnly를 설정하면 페이지의 JavaScript에서 해당 쿠키 값을 읽을 수 없다. 하지만 브라우저는 조건에 맞는 요청에 쿠키를 자동으로 보내므로 로그인 기능은 동작한다.

이 설정은 악성 JavaScript가 쿠키 속 토큰을 직접 읽어 탈취하는 위험을 줄인다. 다만 악성 코드가 사용자 대신 요청하는 것까지 모두 막지는 않는다.

따라서 HttpOnly만으로 보안 처리가 끝나는 것은 아니다.

현재 구현에는 SameSite 설정과 변경 요청의 CSRF 토큰·출처 검사도 포함했다. 운영 배포에서는 HTTPS와 Secure 쿠키 설정까지 확인해야 한다.

참고: [MDN — 쿠키 사용](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies)

## 7. 로그인 성공과 데이터 접근 허용은 별개다

인증과 인가도 구분했다.

- **인증:** 누구인지, 로그인 상태가 유효한지 확인한다.
- **인가:** 그 사용자가 요청한 작업을 해도 되는지 확인한다.

로그인한 멤버라고 해서 모든 제품의 백업을 다운로드할 수 있으면 안 된다.

우리 제품은 요청마다 현재 역할과 담당 제품을 확인한다. 멤버는 담당 제품만 이용할 수 있고, 관리 기능은 별도의 권한을 요구한다.

화면에서 버튼을 숨기는 것으로 끝내지 않고, API에서도 같은 검사를 수행한다. 사용자가 화면을 거치지 않고 API를 직접 호출할 수도 있기 때문이다.

## 8. 회사 IP 기반 접근 제한을 추가할 계획이다

앞으로는 서버가 확인한 접속 IP가 사전에 등록한 회사의 허용 IP와 일치하는 경우에만 로그인할 수 있도록 제한할 계획이다.

로그인 이후의 데이터 조회·다운로드 요청에도 같은 제한을 적용해, 허용된 회사 네트워크 밖에서는 이용할 수 없도록 할 예정이다.

현재 개발 서버를 localhost에서 실행하는 설정과 회사망 접속 제한은 다르다. 회사 IP 허용 목록 검사는 아직 구현하지 않았다.

프록시 뒤에서 실행한다면 실제 접속 IP를 어떤 경로로 신뢰할지도 정해야 한다. IP 제한은 허용된 네트워크를 통한 접속인지 확인하는 것이며, 물리적으로 사무실에 있는 사람임을 증명하지는 않는다.

IP 제한은 사용자 인증을 대체하지 않는다. 허용된 네트워크에서 접속했더라도 계정 인증과 제품별 권한 검사는 별도로 수행한다.

## 9. 보안을 고려했다는 말과 보안이 완성됐다는 말은 다르다

이번에 적용한 것은 로그인 보호의 일부다.

- 사전 등록 계정만 로그인 허용
- 비밀번호 해시 저장
- JWT 서명과 만료 시간 검증
- 서버 세션을 통한 로그아웃·비밀번호 변경 반영
- HttpOnly 쿠키와 CSRF 방어
- 로그인 시도 제한
- 서버에서 역할·담당 제품 권한 검사

운영에 앞서 계정 발급과 비밀번호 정책, HTTPS, 회사망 접근 제한, 추가 인증, 인증·다운로드 감사 기록 등을 보완해야 한다.

백업 파일의 저장·암호화·다운로드 이후 관리 역시 로그인과 별도로 다뤄야 한다. 로그인 기능 하나로 제품 전체의 데이터 보안이 완성되지는 않는다.

참고: [OWASP — 인증 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

이번에 가장 크게 배운 것은 특정 기술을 선택했다는 사실보다 **각 장치가 무엇을 막고, 무엇은 막지 못하는지 설명하는 것**이 중요하다는 점이다.

JWT, 서버 세션, 쿠키는 각각 역할이 다르다. 그 역할을 구분하고 나니 왜 함께 사용하는지, 어디를 더 보완해야 하는지도 조금씩 설명할 수 있게 됐다.
