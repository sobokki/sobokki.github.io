> 캐시 히트율이 낮다고 바로 메모리를 늘리지 않았다. 먼저 어떤 작업이 디스크를 많이 읽는지 추적했다.

## 상황 — 캐시 히트율이 94.8%로 내려갔다

다지점 병원의 매출 데이터를 분석하는 서비스를 개발하던 중 PostgreSQL 캐시 히트율이 주의 기준인 95% 아래로 내려갔다는 알림을 받았다.

화면에 표시된 수치는 94.8%였다.

알림에는 다음과 같은 조치가 필요하다고 적혀 있었다.

- `shared_buffers` 증설
- 쿼리 최적화
- 인덱스 최적화

처음에는 DB에 할당된 메모리가 부족한 문제라고 생각하기 쉬웠다. 하지만 캐시 히트율 하나만 보고 메모리를 늘리면 실제 원인을 가릴 수 있다.

먼저 다음 내용을 확인하기로 했다.

- 어느 데이터베이스에서 발생한 경고인가?
- 특정 시간대에만 낮아졌는가?
- 자동 동기화 작업과 시간이 겹쳤는가?
- 사용자가 대시보드를 조회한 시간과 겹쳤는가?
- 실제로 디스크를 많이 읽은 쿼리는 무엇인가?
- 같은 시간에 API 응답도 느려졌는가?

캐시 히트율이라는 결과보다 그 숫자를 만든 작업을 먼저 찾는 것이 목표였다.

## 캐시 히트율이란 무엇인가

PostgreSQL은 자주 사용하는 데이터 블록을 메모리의 버퍼 캐시에 보관한다.

이를 책상과 창고에 비유할 수 있다.

- 버퍼 캐시: 책상 위에 올려 둔 자료
- 캐시 히트: 필요한 자료를 책상에서 바로 찾음
- 디스크 읽기: 책상에 없어 창고에서 자료를 가져옴

캐시 히트율은 일반적으로 다음과 같이 계산한다.

```text
캐시 히트율 = hit / (hit + read) × 100
```

히트율이 94.8%라면 지금까지 요청한 데이터 블록 중 약 94.8%는 메모리에서 찾았고, 나머지는 디스크에서 읽었다는 뜻이다.

하지만 이 숫자만으로는 현재 서비스가 느리다고 단정할 수 없다.

PostgreSQL의 `heap_blks_hit`, `heap_blks_read` 같은 통계는 최근 몇 분의 값이 아니라 통계가 시작된 뒤부터 계속 누적된 값이기 때문이다.

과거에 큰 조회가 한 번 발생했다면 문제가 해결된 후에도 낮은 비율이 오랫동안 남아 있을 수 있다.

## 해결 과정 1 — 먼저 추적할 수 있는 환경을 만들었다

처음 경고를 받았을 때는 DB별 1분 단위 읽기량과 쿼리별 실행 기록이 충분하지 않았다.

현재 값은 확인할 수 있었지만, 경고가 발생한 시간으로 돌아가 어떤 작업이 실행됐는지 확정하기 어려웠다.

그래서 다음 기록을 보강했다.

1. 데이터베이스별 메모리·디스크 읽기량 수집
2. API 요청별 응답시간 로그 보존
3. 자동 동기화 작업의 시작·완료·실패·소요시간 기록
4. PostgreSQL Query Store 활성화
5. `EXPLAIN (ANALYZE, BUFFERS)`를 이용한 실행 계획 확인

이후부터는 경고 시각과 실제 쿼리를 연결할 수 있게 됐다.

```text
경고 발생 시각
  → 같은 시각의 API 요청 확인
  → 같은 시각의 자동 동기화 확인
  → Query Store에서 디스크를 많이 읽은 쿼리 확인
  → EXPLAIN으로 실제 실행 방식 재현
```

추측해서 코드를 바꾸기보다 원인이 보일 때까지 관측 환경을 먼저 만든 셈이다.

## 해결 과정 2 — 대시보드의 반복 조회를 합쳤다

매출 대시보드는 한 화면에서 여러 분석 결과를 보여준다.

- 핵심 매출 지표
- 매출 추이
- 지점별 순위
- 직원별 성과
- 신환·구환 분석
- 요일별 패턴
- 인구통계
- 채널 기여도

기존 화면은 각 영역을 별도 API로 요청했다. 서버도 영역마다 같은 기간의 매출 데이터를 다시 조회하고 계산했다.

```text
개선 전

대시보드 진입
  ├─ 핵심 지표 요청
  ├─ 매출 추이 요청
  ├─ 지점 순위 요청
  ├─ 직원 성과 요청
  ├─ 신환·구환 요청
  ├─ 요일별 패턴 요청
  ├─ 인구통계 요청
  └─ 채널 기여도 요청
```

먼저 핵심 지표와 채널 기여도에서 중복으로 실행하던 집계를 합쳤다.

다음 단계에서는 화면의 분석 요청 8개를 통합 API 하나로 묶었다. 선택 기간의 매출 데이터를 한 번 준비하고 여러 계산에서 재사용하도록 변경했다.

```text
개선 후

통합 API 요청 1회
  → 선택 기간 매출 데이터 준비 1회
    ├─ 핵심 지표 계산
    ├─ 매출 추이 계산
    ├─ 직원 성과 계산
    ├─ 신환·구환 계산
    ├─ 요일별 패턴 계산
    ├─ 인구통계 계산
    └─ 채널 기여도 계산
```

모든 쿼리를 무조건 하나로 합치지는 않았다.

직전 기간과 전년 동기처럼 조회 범위가 다른 데이터는 결과의 정확성을 유지하기 위해 별도로 집계했다. 같은 조건과 같은 원본을 사용하는 계산만 안전하게 재사용했다.

## 해결 과정 3 — CSV의 N+1 조회를 묶음 처리로 바꿨다

외부 광고 플랫폼에서 받은 고객 CSV를 업로드하면 유입 고객과 실제 매출 고객을 연결한다.

기존에는 CSV의 각 행을 처리할 때마다 다음 조회를 반복했다.

1. 이미 연결된 고객인지 확인
2. 유입 데이터 조회
3. 이름과 전화번호가 일치하는 매출 고객 검색
4. 연결 결과 저장

파일이 커질수록 DB 조회 횟수가 행 수에 비례해 증가하는 N+1 형태였다.

이를 다음과 같이 변경했다.

- 업로드 직후 메모리에 있는 데이터를 그대로 사용
- 기존 연결 결과를 ID 목록으로 한 번에 조회
- 이름과 정규화한 전화번호 조합을 중복 제거
- 매출 고객 후보를 여러 건씩 묶어서 조회
- 연결 결과도 일괄 저장
- 입력이 매우 크면 DB 파라미터 한도를 넘지 않도록 일정 크기로 분할

단건 처리와 CSV 처리도 같은 내부 매칭 로직을 사용하게 했다. 처리 방식이 달라져도 고객 연결 결과는 같아야 하기 때문이다.

## 해결 과정 4 — 자동 동기화에 체크포인트를 도입했다

외부 CRM의 매출 데이터는 매일 자동으로 동기화된다.

실제로 새로 들어오는 데이터는 많지 않았지만, 기존 구현은 어떤 날짜까지 처리했는지 확인하기 위해 큰 매출 테이블을 매일 다시 조회했다.

새 데이터를 저장하는 작업보다 이미 처리한 파일인지 확인하는 작업이 더 많은 데이터를 읽고 있었다.

```text
개선 전

매일 자동 동기화
  → 과거 매출 기록 조회
  → 지점·날짜별 마지막 처리 시각 계산
  → 새 파일 선별
```

이를 작은 체크포인트 테이블을 사용하는 방식으로 변경했다.

```text
개선 후

매일 자동 동기화
  → 작은 체크포인트 조회
  → 새 파일 선별
  → 저장에 성공한 파일만 체크포인트 갱신
```

매출 데이터 저장과 체크포인트 갱신은 같은 트랜잭션에서 처리했다.

파일 다운로드, 검증 또는 DB 저장이 실패하면 체크포인트도 갱신되지 않는다. 다음 실행에서 실패한 파일을 안전하게 다시 시도할 수 있다.

이후 자동 동기화는 과거 매출 테이블 전체를 뒤져 마지막 처리 위치를 찾지 않아도 됐다.

## 해결 과정 5 — 전체 지점 조회에 맞는 인덱스를 추가했다

반복 조회를 줄인 뒤에도 특정 사용자 요청에서 큰 디스크 읽기가 남아 있었다.

Query Store로 확인한 쿼리는 본사 관리자가 모든 지점의 직전 기간과 전년 동기 매출을 비교하는 집계였다.

실행 계획을 확인해 보니 약 66만 건을 전체 조회한 뒤 날짜 조건에 해당하는 약 8.9만 건을 골라 합계를 계산하고 있었다.

당시 매출 테이블에는 다음 복합 인덱스가 있었다.

```sql
CREATE INDEX ON sales_records (branch_id, sales_date);
```

이 인덱스는 다음과 같은 조회에 적합하다.

```text
A 지점의 8월 매출
```

하지만 본사 관리자는 지점을 선택하지 않으면 모든 지점을 조회한다.

```text
전체 지점의 8월 매출
```

이 쿼리에는 `branch_id` 조건이 없고 날짜 조건만 있다.

PostgreSQL의 다중 컬럼 B-tree 인덱스는 선두 컬럼에 조건이 있을 때 가장 효율적이다. 지점이 첫 번째인 기존 인덱스만으로는 전체 지점의 날짜 범위를 효과적으로 좁히기 어려웠다.

기존 인덱스는 지점별 조회를 위해 유지하고, 날짜 단일 인덱스를 추가했다.

```sql
CREATE INDEX CONCURRENTLY ix_sales_records_sales_date
ON sales_records (sales_date);
```

조회 SQL이나 사용자 권한은 변경하지 않았다.

본사 관리자는 여전히 모든 지점의 데이터를 조회한다. PostgreSQL이 필요한 날짜의 행부터 찾을 수 있도록 접근 경로만 추가했다.

운영 중 인덱스를 일반적인 방식으로 생성하면 데이터 저장 작업이 기다릴 수 있다. 그래서 insert, update, delete를 장시간 막지 않는 `CONCURRENTLY` 방식으로 생성했다.

## 같은 조건으로 개선 효과를 검증했다

인덱스가 DB에 존재하는 것만으로는 충분하지 않다.

PostgreSQL이 실제 문제 쿼리에서 새 인덱스를 선택하는지 확인해야 한다.

STG와 비슷한 조건으로 약 66만 건의 테스트 데이터를 만들었다. 그중 약 8.9만 건이 비교 기간에 포함되도록 구성하고 같은 SQL을 인덱스 적용 전후에 실행했다.

| 측정 항목 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 실행 계획 | Parallel Seq Scan | Parallel Bitmap Heap Scan | 날짜 인덱스 사용 |
| 확인한 DB 블록 | 15,489개 | 4,981개 | 약 68% 감소 |
| 쿼리 실행시간 | 17.3ms | 10.3ms | 약 40% 감소 |

실행시간은 로컬 테스트 환경에서 나온 값이다. 실제 운영 응답시간으로 그대로 일반화할 수는 없다.

반면 같은 데이터와 같은 SQL에서 PostgreSQL의 실행 계획이 바뀌고, 읽은 블록이 줄어든 것은 개선 방향이 맞다는 근거가 된다.

STG 배포 후에도 새 인덱스가 유효한 상태인지와 실제 사용 횟수가 증가하는지 확인했다.

첫 번째 대시보드 요청은 약 3.16초가 걸렸다. 동일한 조건의 두 번째 요청은 약 0.29초가 걸렸다.

두 번째 요청 구간에는 다음과 같은 차이가 있었다.

```text
메모리에서 찾은 블록: 49,396
추가 디스크 읽기: 18
해당 구간의 계산상 히트율: 약 99.96%
```

첫 요청은 비어 있던 캐시를 채우는 과정이 포함됐고, 두 번째 요청은 캐시가 준비된 상태였다.

한두 번의 요청만으로 서비스의 평균 성능을 말할 수는 없다. 따라서 0.29초를 일반적인 성능 개선율로 표현하지 않고, 장기적으로는 p50, p95, p99 응답시간을 비교하기로 했다.

## 수정했는데도 화면은 왜 계속 94.8%였을까

배포 후 쿼리는 새 인덱스를 사용했다. 최근 요청 구간의 히트율도 약 99.96%였다.

그런데 모니터링 화면은 계속 94.7~94.8%를 표시했다.

원인은 모니터링 화면이 최근 구간이 아니라 PostgreSQL의 누적 통계로 상태를 판단하고 있었기 때문이다.

```text
과거부터 누적된 메모리 적중: 약 8,825만 블록
과거부터 누적된 디스크 읽기: 약 493만 블록
누적 히트율: 약 94.7%
```

새 요청이 좋아져도 과거에 발생한 수백만 건의 디스크 읽기가 분모에 남아 있어 누적 비율은 바로 움직이지 않는다.

이는 코드가 반영되지 않았다는 뜻이 아니었다.

DB 통계를 초기화하면 화면 숫자는 바로 달라질 수 있다. 하지만 원인 분석에 필요한 과거 기록도 함께 사라진다. 숫자를 정상처럼 보이게 만들기 위해 통계를 초기화하는 것은 해결책이 아니다.

경고는 누적값이 아니라 최근 수집 구간의 증가량으로 계산해야 한다.

```text
최근 hit  = 현재 누적 hit  - 이전 누적 hit
최근 read = 현재 누적 read - 이전 누적 read

최근 히트율
  = 최근 hit / (최근 hit + 최근 read) × 100
```

누적 히트율은 장기 참고 지표로 보여주고, 장애 경고와 복구 판단은 최근 5분이나 이전 수집 이후의 변화량을 사용하는 것이 적절하다.

## 하지 않은 것

### 메모리부터 늘리지 않았다

메모리를 늘리면 일부 현상은 완화될 수 있다.

하지만 같은 데이터를 반복해서 읽거나 전체 테이블을 조회하는 구조는 남는다. 불필요한 읽기를 제거한 뒤에도 메모리가 부족하다는 근거가 있을 때 조정하는 것이 맞다고 판단했다.

### 본사 조회 범위를 줄이지 않았다

전체 지점 데이터는 본사 관리자가 반드시 확인해야 하는 요구사항이다.

성능을 위해 일부 지점만 조회하도록 바꾸지 않고, 동일한 데이터를 더 효율적으로 찾게 했다.

### 캐시 통계를 초기화하지 않았다

경고 화면을 초록색으로 바꾸는 것과 시스템을 개선하는 것은 다른 문제다.

과거 진단 기록을 유지하고 실제 요청의 실행 계획, 인덱스 사용 여부, 구간별 읽기량으로 개선 결과를 확인했다.

## 배운 것

### 비율 하나보다 집계 구간이 중요하다

누적 히트율 94.8%와 최근 요청 히트율 99.96%는 동시에 참일 수 있다.

모니터링 수치를 볼 때는 반드시 측정 대상, 집계 기간, 통계 초기화 시점을 함께 확인해야 한다.

### 원인을 볼 수 없다면 관측 환경부터 만들어야 한다

원인을 모르는 상태에서 인덱스와 메모리 설정을 바꾸면 개선 효과를 증명하기 어렵다.

API 로그, DB별 시계열, Query Store를 연결하고 나서야 자동 동기화와 사용자 조회를 구분할 수 있었다.

### 작은 쿼리의 반복과 큰 쿼리 한 번은 해결 방법이 다르다

작은 쿼리가 여러 번 실행되는 문제는 묶음 처리와 데이터 재사용으로 해결했다.

큰 테이블을 한 번 전체 조회하는 문제는 실행 계획을 확인하고 실제 조회 조건에 맞는 인덱스를 추가했다.

### 인덱스는 실제 조회 조건을 기준으로 설계해야 한다

`(지점, 날짜)` 인덱스가 있다고 해서 날짜만 사용하는 조회까지 항상 빨라지는 것은 아니었다.

병원 한 곳을 조회하는 조건과 본사가 모든 지점을 조회하는 조건은 다르다. 인덱스도 실제 SQL에 맞춰 검토해야 한다.

### 개선 수치는 같은 조건으로 비교해야 한다

캐시가 비어 있는 첫 요청과 캐시가 준비된 두 번째 요청을 단순 비교하면 안 된다.

같은 데이터, 같은 SQL, 같은 필터에서 실행 계획과 읽은 블록을 비교하고 실제 트래픽에서는 일정 기간의 p95와 p99를 확인해야 한다.

## 마치며

이번 문제는 DB가 고장난 장애가 아니었다.

데이터가 늘어나면서 기존 조회 방식의 비용이 드러난 성능 경고였다.

캐시 히트율 94.8%를 보고 바로 메모리를 늘렸다면 숫자는 일시적으로 좋아졌을 수 있다. 하지만 대시보드의 중복 조회, CSV의 행별 반복 조회, 자동 동기화의 과거 데이터 확인, 전체 지점 조회의 전체 테이블 스캔은 그대로 남았을 것이다.

우리는 먼저 관측 환경을 만들고 실제로 많이 읽는 흐름을 찾았다.

그 결과 같은 데이터를 재사용하고, 여러 행을 묶어서 처리하고, 동기화 위치를 체크포인트로 남기고, 실제 조회 조건에 맞는 인덱스를 추가할 수 있었다.

이번 작업에서 얻은 가장 큰 교훈은 단순하다.

> 성능 경고의 숫자를 고치기보다, 그 숫자를 만든 작업을 먼저 찾아야 한다.
