> 조각을 더 잘게 쪼개는 쪽으로 두 번 갔다.
> 답은 **같은 데이터를 두 번 읽지 않는 것**이었다.

## 어떤 작업이었나

SNS 게시물의 조회수·좋아요 같은 지표를 모아서 화면에 보여주는 기능이다.

데이터를 모으는 방식은 이렇다.

1. 게시물을 주기적으로 들여다보고 그때의 조회수를 기록한다 (= **관측**)
2. 한 게시물에 관측이 여러 개 쌓인다 (조회수가 어떻게 늘었는지 알 수 있다)
3. 1시간마다 그걸 계산해서 「지금 조회수」, 「증가 속도」 같은 값을 만든다
4. 화면은 그 결과를 보여준다

3번이 이 글의 주인공이다. **배치 작업**이라고 부른다. 사람이 기다리지 않는 뒤에서 도는 작업이다.

그리고 이 계산을 한 번 돌리는 것을 **회차**라고 부르겠다. 1시간마다 한 회차가 돈다.

## 상황 — 그 배치가 한 번도 끝나지 못했다

운영 DB에서 돌리면 매번 이 에러로 중단됐다.

```
canceling statement due to statement timeout
```

> `statement_timeout` 은 **SQL 한 문장이 정해진 시간을 넘기면 DB가 강제로 끊는** 설정이다.
> 우리는 300초로 걸어 뒀다.

결과 테이블은 계속 0행이었다. 화면에는 「분석 결과를 준비하고 있습니다」만 떠 있었다.

항상 같은 곳에서 멈췄다 — 배치의 첫 단계다.

게시물 본문 14만 건(510MB)을 **한 문장 안에서 전부** 처리하려다 300초를 넘긴다.

### 어디서 돌아가고 있었나

헷갈리기 쉬운 부분이라 먼저 정리한다.

- **DB** — 클라우드에 있다. CPU 1개짜리 저렴한 등급, 디스크 25MB/s, IOPS 120
- **배치 프로그램** — 그때는 **내 노트북**에서 돌렸다 (운영 서버에 배포하기 전이었다)

> IOPS 는 **디스크를 1초에 몇 번 읽고 쓸 수 있는지**를 나타내는 값이다.

그리고 수집한 날것 데이터가 쌓이는 테이블을 **원천 테이블**이라고 부르겠다. 관측 354만 행, 게시물 15만 건이 들어 있다.

사양을 보고 처음 든 생각은 "DB 서버가 작아서 그렇다"였다.

**이게 절반만 맞았다.**

## 먼저 알게 된 것 — "느리다"는 한 가지 문제가 아니었다

끝까지 파 보니 원인이 **세 개**였고, 고치는 방법이 전부 달랐다.

| | 겉으로 보이는 증상 | 실제 원인 |
| --- | --- | --- |
| ① | 300초에 중단된다 | 한 번에 전부 처리한다 |
| ② | 쪼갰는데도 안 끝난다 | 같은 데이터를 복사했다가 다시 읽는다 |
| ③ | 13시간 멈춰 있다 | 끊긴 연결을 무한정 기다린다 |

이게 왜 중요한가.

세 개를 한 덩어리로 보면 **어떤 수정도 효과가 없어 보인다.**

실제로 ①을 고친 뒤 숫자가 거의 안 바뀌어서, "고친 게 효과가 없다"고 결론 낼 뻔했다.

## 1차 시도 — "한 번에 전부"를 쪼갰다

원인이 쿼리 자체가 아니라 **한 번에 다 하려는 것**이라고 봤다. 두 가지를 했다.

### 테이블을 조금씩 끊어 읽게 했다

PostgreSQL은 각 행이 디스크 어디에 있는지를 `ctid` 라는 값으로 알고 있다. 쉽게 말해 **행의 주소**다.

그 주소 범위로 끊어서 32MB씩 읽게 했다.

### 매번 전부 다시 계산하지 않게 했다

바뀐 것만 다시 읽는 방식(**증분**)으로 바꿨다.

여기서 함정이 하나 있었다. **"언제 이후를 다시 읽을지" 기준으로 어떤 컬럼을 쓰느냐**다.

- `updated_at` — 데이터를 **보내는 쪽**이 찍은 시각
- `synced_at` — 데이터를 **받는 쪽**이 찍은 시각

보내는 쪽 시각을 쓰면 **도착 순서와 어긋나서 일부 행이 조용히 빠진다.** 에러도 안 난다. 그래서 받는 쪽 시각을 기준으로 썼다.

### 결과

```
가장 오래 걸리는 SQL 한 문장:  36.1초  →  2.7초
```

숫자는 좋아졌다.

**그런데 작업 전체는 여전히 안 끝났다.** 300초에 멈추던 게 835초까지 버티다 또 멈췄다.

그때 내린 결론은 "쪼개기는 맞았고 조각이 아직 크다"였다.

**이 결론이 틀렸다.**

## 2차 시도 — 진짜 원인은 '두 번 읽기'였다

조각을 더 줄이기 전에, 각 단계가 실제로 뭘 하는지 코드를 다시 읽었다. 그러다 발견했다.

```
[기존]
관측 354만 행  →  임시 테이블에 복사  →  그걸 다시 읽어서  →  게시물별 13.6만 행으로 요약

[수정]
관측 354만 행  →  한 번 읽으면서 바로 게시물별로 요약
```

> **임시 테이블**은 작업 중에만 쓰고 접속이 끊기면 사라지는 테이블이다.

354만 행을 **디스크에 썼다가(복사), 다시 디스크에서 읽고 있었다.**

디스크 속도가 25MB/s인 서버에서 이 왕복이 **전체 비용의 대부분**이었다.

그리고 중요한 점 — **조각을 아무리 잘게 나눠도 왕복 횟수는 그대로다.** 그래서 1차 시도로는 끝까지 갈 수 없었다.

수정은 간단했다. 임시 테이블에 **요약 결과만**(13.6만 행) 담게 했다.

> 게시물은 15만 건인데 요약이 13.6만 행인 이유는, 아직 관측이 하나도 없는 게시물이 있기 때문이다.

읽는 범위와 중복 처리 규칙은 건드리지 않았다. 그래서 **결과 숫자는 하나도 안 바뀐다.**

> 성능 수정에서 이게 중요하다. "결과가 안 바뀐다"를 설명할 수 있어야 믿고 배포할 수 있다.

**이때부터 작업이 끝까지 돌았다.**

## 반대로, 쪼개면 손해인 곳도 있었다

1차 시도가 성공했으니 "관측 테이블도 게시물 ID 구간으로 나누면 더 빠르겠지" 싶었다.

`EXPLAIN` 을 떠 보고 접었다.

> `EXPLAIN` 은 **DB가 이 쿼리를 어떻게 처리할지 미리 보여주는** 명령이다. 실행하기 전에 계획을 볼 수 있다.

결과가 이랬다.

```
구간 조건을 넣으면
  → DB가 구간마다 관측 테이블을 처음부터 끝까지 전부 읽는다
     (354만 행 기준 98,238 page = 테이블 전체)
배치를 15개로 나누면
  → 관측 테이블을 15번 읽는다
```

> 인덱스를 안 쓰고 테이블을 처음부터 끝까지 읽는 걸 **seq scan**(순차 스캔)이라고 한다.

즉 **쪼개면 15배 느려진다.**

같은 작업 안에서도 **어떤 단계는 쪼개야 하고, 어떤 단계는 쪼개면 안 된다.**

**게시물 본문을 읽을 때는 통한 방법이, 관측을 읽을 때는 함정이었다.**

안 쪼갠 이유를 코드 주석·설정·문서 세 군데에 남겼다. 6개월 뒤에 누군가(아마 나)가 "여기 왜 안 쪼갰지?" 하고 물을 자리라서다.

## 지우고 싶었지만 지우면 안 됐던 것

원천에 **중복 관측**이 섞여 있었다. 같은 게시물이 같은 시각으로 두 번 기록된 행이다.

세어 보니 **5,136행, 전체의 0.148%**다. (왜 생기는지는 수집하는 쪽 문제라 이 글의 범위는 아니다.)

비율이 작으니 중복 제거를 빼면 더 빨라진다. 빼 보려다 멈췄다.

빼면 이렇게 된다.

1. 관측 횟수가 실제보다 부풀어 보인다
2. 최근 조회수 2건이 **같은 시각**으로 잡힌다
3. 시간 간격이 0이 된다
4. 「측정 간격이 너무 짧음」으로 **잘못 분류된다**

**0.148%가 결과를 거짓으로 만드는 길이 있었다.**

그래서 중복 제거를 유지하고, 두 시각 모두 중복인 경우까지 테스트로 막아 뒀다.

## 3차 — 한 회차가 13시간 넘게 끝나지 않았다

2차까지 고치고 나니 배치가 3분대에 끝났다. 이제 됐다고 생각했다.

그런데 며칠 뒤 기록을 보니 이런 회차가 하나 있었다.

```
요청 10-06 10:55   실패   811분 55초 (= 13.5시간)
```

**1시간마다 돌고, 보통 3분에 끝나는 작업이 13시간 30분을 쓰고 실패했다.**

또 성능 문제인가 했다. 아니었다.

느려서 오래 걸린 게 아니라, **아무 일도 안 하면서 기다리고 있었다.**

### 왜 기다리고 있었나

앞에서 말했듯 배치는 **내 노트북**에서 돌고, DB는 클라우드에 있었다.

그 노트북이 절전에 들어가면서 DB로 가는 연결이 끊겼다.

그런데 작업은 그걸 몰랐다. **끊긴 연결에서 응답이 올 거라고 믿고 계속 기다렸다.**

더 나빴던 건 그다음이다.

- 스케줄러에 "같은 작업을 동시에 두 개 돌리지 않는다" 설정이 걸려 있다
- 그래서 그 13시간 동안 **다음 회차 14번이 전부 건너뛰어졌다**
- 멈춘 기록을 정리하는 코드는 **다음 회차가 시작할 때만** 돌기 때문에 정리도 안 됐다
- 결국 사람이 손으로 그 기록을 닫아야 풀렸다

### 이미 있던 안전장치가 왜 하나도 안 먹었나

이게 이 글에서 가장 배운 부분이다.

| 안전장치 | 왜 안 먹었나 |
| --- | --- |
| `statement_timeout` 300초 | **DB 서버가 에러를 보내 주는** 방식이다. 연결이 끊기면 그 에러가 올 길이 없다 |
| `connect_timeout` 5초 | **접속하는 동안만** 지켜본다. 접속한 뒤의 기다림은 안 본다 |
| advisory lock | 연결이 끊기면 DB가 알아서 풀어 준다. 원인이 아니었다 |

**"상한을 걸어 뒀다"가 "반드시 끝난다"를 뜻하지 않는다.**

### 어떻게 고쳤나

두 가지를 넣었다.

**1) TCP keepalive 를 켰다.**

> 연결이 살아 있는지 주기적으로 찔러 보는 기능이다. 답이 없으면 끊어진 걸로 판단한다.

60초 쉬었다가 10초 간격으로 6번 찔러 본다. **최대 120초 안에 끊김을 감지한다.**

**2) 작업 전체에 30분 상한을 걸었다.**

여기서 순서가 중요하다. **keepalive 가 없으면 상한만으론 안 된다.**

쓰는 DB 드라이버(psycopg 3)는 기다림이 취소되면 **같은 연결을 다시 기다린다.** 그래서 끊긴 연결에서는 애플리케이션 상한만으론 빠져나올 수 없다.

keepalive 가 그 재시도를 에러로 끝내 줘야 상한이 작동한다.

**3) 정리 작업에도 각각 10초 상한을 뒀다.**

정리하다가 또 매달리면 똑같은 함정이다. 10초 안에 안 되면 포기하고, 다음 회차가 정리한다.

## 그래서 화면은 왜 빠른가

여기까지가 "배치를 끝까지 돌게 만든" 이야기다.

그런데 **애초에 왜 배치로 하는가**를 같이 알아야 전체가 이해된다.

답은 간단하다. **화면이 요청할 때 계산하면 쓸 수 없다.**

같은 DB, 같은 순간에 재 봤다.

| | 걸린 시간 |
| --- | --- |
| 원천 관측 354만 행을 **그냥 한 번 세기만** | **67,386 ms** (67초) |
| 미리 계산해 둔 결과에서 **조회수 상위 50개 가져오기** | **240 ms** |

공정한 비교는 아니다. 왼쪽은 그냥 센 것이고, 실제 계산(중복 제거·증감·중간값 등)은 **3분 30초**가 걸린다.

요점은 이것이다. **화면이 원천 데이터를 건드릴 여유가 아예 없다.**

### 구조

```
수집
  ↓
원천 테이블 (관측 354만 · 게시물 15만)
  ↓   1시간마다 배치 (3분 30초)
결과 테이블 (게시물별 1행 + 회차별 집계)
  ↓   조회 API — 「가장 최근에 성공한 회차」만 읽는다
화면 (0.24초)
```

### 빠른 이유 4가지

**1) 미리 계산해 둔다**

한 게시물에 관측이 여러 개 쌓이지만, 화면이 알고 싶은 건 「지금 조회수」와 「증가 속도」다.

그 계산을 1시간마다 미리 해서 **게시물별 1행**으로 만들어 둔다.

**2) 회차(run) 단위로 묶는다**

앞에서 말한 **회차**가 여기서 중요해진다. 결과 행마다 회차 번호를 붙여 둔다.

조회는 **성공한 가장 최근 회차만** 읽는다.

그래서 **계산 중인 회차가 화면에 섞이지 않는다.** 사용자가 "반쯤 계산된 숫자"를 볼 일이 없다.

**3) 인덱스를 전부 '회차'로 시작하게 깔았다**

결과 테이블은 회차마다 쌓인다. 지금 **1,307만 행**이다. **원천보다 크다.**

그런데도 빠른 이유가 이 인덱스다.

```
(회차, 조회수)      ← 화면 기본 정렬
(회차, 작성일)
(회차, 계정)
(회차, 분야)
(회차, 목록조건)
```

> 두 컬럼을 묶은 걸 **복합 인덱스**라고 한다. 앞 컬럼으로 먼저 좁히고 뒤 컬럼으로 정렬한다.

앞이 전부 `회차` 라서, 1,307만 행 중 **최신 회차 14.9만 행만 25ms 에 집어낸다.**

화면의 정렬·필터 조합마다 인덱스를 하나씩 둔 셈이다.

**4) 안 변하는 값은 회차에서 뺐다**

게시물의 줄 수 같은 값은 관측과 상관없는 **고정값**이다.

그래서 회차마다 쌓이는 테이블이 아니라 **게시물 단위 테이블**에 따로 뒀다.

회차를 88번 돌렸는데도 그 테이블은 14.9만 행(= 게시물 수)에서 안 늘었다.

회차마다 복제했다면 1,300만 행이 더 쌓였을 것이다.

## 검증

고친 뒤 며칠을 돌려 보고, 그다음 운영 서버에 배포했다. 노트북 없이도 도는 상태가 된 것이다.

```
집계 회차 114회 중 113회 성공   (실패 1건 = 위의 13.5시간 건)
걸린 시간 3~5분, 대부분 3분대
운영 서버에서 돈 첫 회차 3분 28초
```

한 가지가 눈에 띈다.

배치를 **노트북에서 돌릴 때와 운영 서버에서 돌릴 때가 똑같이 3분대**였다.

무거운 일이 전부 DB 안에서 일어나기 때문이다. 배치 프로그램이 어느 기계에서 도는지는 거의 영향이 없었다.

**고쳐야 할 곳이 애플리케이션이 아니라 DB에 보내는 작업의 모양이었다**는 뜻이기도 하다.

## 하지 않은 것

**서버 사양을 올리지 않았다.**

처음엔 "코드로 되나 / 증설이 필요하나"가 갈림길이라고 봤다. 답은 코드였다.

증설을 먼저 했으면 왕복을 영원히 못 찾았을 것이다.

**조각을 더 잘게 쪼개지 않았다.**

그 방향으로 두 번 갔고, 두 번 다 답이 아니었다.

**중복 제거를 빼지 않았다.**

0.148%가 결과를 거짓으로 만드는 길이 있었다.

**접속 타임아웃 5초는 그대로 뒀다.**

실제 접속 시간이 2.45~5.05초라 아슬아슬하게 걸리는 걸 안다.

그런데 이 값은 **사람이 기다리는 조회 경로와 공유**한다. 배치만 따로 둘지는 별도 판단으로 남겼다.

**고칠 수 있다고 지금 고쳐야 하는 건 아니다.**

## 배운 것

**1. "느리다"는 증상 이름일 뿐이다**

원인을 세 겹으로 가르기 전에는 어떤 수정도 효과가 없어 보였다.

한 층만 고치고 숫자를 보면 "효과 없음"으로 잘못 결론 낸다.

**2. 직전에 통한 방법이 다음 단계의 함정이 된다**

쪼개기로 36초를 2.7초로 줄인 성공이, "관측도 쪼개자"는 오답으로 이어졌다.

`EXPLAIN` 을 안 떴으면 15배 느려진 걸 들고 "왜 더 느려졌지?" 하고 있었을 것이다.

**3. 타임아웃은 '누가 보내 주는지'를 알아야 한다**

`statement_timeout` 은 DB 서버가 보내 주는 에러다. 연결이 끊기면 그 길 자체가 없어진다.

상한을 걸어 뒀다고 반드시 끝나는 게 아니다.

**4. 빠른 화면은 빠른 쿼리가 아니라 '미리 계산해 둔 결과'에서 나온다**

대신 값을 치른다.

- 데이터가 최대 1시간 늙는다 (실시간이 아니다)
- 결과 테이블이 원천보다 커진다

이 교환을 알고 고르는 것이 설계다.
